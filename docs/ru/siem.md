# Мониторинг безопасности и SIEM

Отдельные средства защиты (межсетевой экран, IPS, антивирус, DHCP snooping, DAI) работают каждое на своём участке. Чтобы увидеть атаку целиком и вовремя, их события собирают в одном месте — это и есть **мониторинг** и **SIEM** (Security Information and Event Management). NetEmu показывает, как это выглядит: «Инструменты → Мониторинг (SIEM)» собирает события со всех устройств и мониторов безопасности и превращает их в тревоги.

## Зачем это нужно

Атака редко видна по одному событию. Её складывают из признаков на разных устройствах:
- на коммутаторе — нарушения port security, отброшенные поддельные ARP (DAI), захват корня STP;
- на маршрутизаторе и межсетевом экране — срабатывания ACL, IPS, всплески трафика;
- на серверах — перегрузка, отказы в обслуживании (503), неудачные входы по SSH;
- в сети — сканирование портов, обращения к командным серверам, утечка данных.

Просматривать каждое устройство вручную долго и ненадёжно. Центр мониторинга (SOC) собирает журналы со всех источников, **коррелирует** их (связывает в одно событие) и выдаёт **тревоги** с важностью и рекомендацией. Так атаку видно в первые минуты.

## Как это устроено

1. **Сбор журналов.** Устройства отправляют события по **syslog** на центральный сервер (`logging host <ip>`). Серверы, антивирусы, IPS и межсетевые экраны тоже пишут журналы. В больших сетях используют сборщики (rsyslog, Graylog, Elastic/Logstash, Splunk).
2. **Нормализация.** Записи из разных форматов приводят к единому виду (время, источник, тип, важность).
3. **Корреляция и правила.** Правила обнаружения связывают события: «много неудачных входов SSH с одного адреса» → подбор пароля; «подключения к одному порту по всем адресам подряд» → сканирование; «периодические обращения к одному внешнему адресу» → связь с командным сервером; «поток выше порога» → DDoS.
4. **Тревоги и реагирование.** Сработавшее правило создаёт тревогу (важность, описание, рекомендация). Аналитик проверяет её и принимает меры; часть действий автоматизируют (SOAR).
5. **Хранение.** Журналы хранят для расследований и отчётности (нормативные требования).

Полезные практики: синхронизация времени по **NTP** (иначе события не сопоставить), защита самих журналов от подделки, разумные пороги, чтобы тревоги не тонули в шуме.

## SIEM в NetEmu

«Инструменты → Мониторинг (SIEM)» (`Ctrl+Shift+M`) — единое окно:
- **Тревоги** по важности (критический / высокий / средний / низкий): категория, источник, что обнаружено. При выборе строки внизу появляется рекомендация.
- **Журнал событий** — объединённая лента со всех мониторов безопасности (DDoS, заражение, атаки L2) и из syslog-буферов устройств.

SIEM в NetEmu обнаруживает:

| Категория | Признак | Рекомендация |
|---|---|---|
| DDoS | перегрузка канала или ресурсов сервера | очистка у провайдера, лимиты, SYN cookies |
| Сканирование | много пакетов-эксплойтов | сегментация, IPS |
| Червь/вредонос | заражённые узлы, шифрование | изоляция, лечение, закрытие уязвимости |
| Командный сервер | обращения к C2, утечка данных | блокировка C2 (ACL/DNS sinkhole) |
| Подмена ARP | отравление ARP, перехват | Dynamic ARP Inspection |
| Переполнение MAC | переполнение таблицы коммутации | port security |
| Атака STP | захват корня дерева | BPDU Guard / Root Guard |
| IPS/IDS | отброшенные вредоносные пакеты | защита работает |

Чтобы устройства слали события в syslog, настройте на них `logging host <ip>` и поднимите Syslog-сервер (Linux-сервер → «Службы», или `cat /var/log/syslog`). Синхронизируйте время по NTP.

## Ограничения модели

- SIEM в NetEmu — учебная модель: правила обнаружения встроены и срабатывают по состоянию мониторов безопасности и syslog-буферов, а не по полноценному языку корреляции.
- Нет долговременного хранилища и отчётов; тревоги вычисляются по текущему состоянию сети.
